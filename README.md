# Аналіз та оптимізація даних Spotify у MongoDB

## 1. Налаштування оточення

**Вимоги:**

- Python 3.10+
- MongoDB Atlas (M0 Shared)
- Утиліта `mongosh`

**Порядок запуску:**

1. Клонувати репозиторій та встановити залежності:
   ```bash
   pip install -r requirements.txt
   ```
2. Створити файл `.env` у корені проєкту та додати рядок підключення до MongoDB Atlas:
   ```env
   MONGO_URI="mongodb+srv://<USER>:<PASSWORD>@<CLUSTER>.mongodb.net/"
   ```
3. Завантажити сирі дані (CSV) у базу `spotify` (колекція `tracks_raw`):
   ```bash
   python scripts/01_load_data.py
   ```
4. Виконати трансформацію даних (створення колекції `tracks`):
   ```bash
   mongosh "mongodb+srv://..." scripts/02_transform.js
   ```
5. Виконати запити та перевірити індекси:
   ```bash
   mongosh "mongodb+srv://..." queries/part2_queries.js
   mongosh "mongodb+srv://..." queries/part3_indexes.js
   ```

## 2. Схема даних (Частина 1)

Під час трансформації плоска CSV-структура була перетворена на документоорієнтовану.

- Рядок виконавців розбито на масив `artists`.
- Усі числові метрики треку згруповано у вкладений об'єкт `audio_features`.
- Додано обчислювані поля `duration_sec` та `popularity_tier`.

### Відповіді на теоретичні питання (Частина 1)

**1. Чому аудіо-характеристики винесені в окремий об’єкт `audio_features`, а не зберігаються плоско?**
Винесення логічно пов'язаних атрибутів у вкладений об'єкт відповідає принципам документоорієнтованого моделювання.

- _Коли вигідне:_ Це покращує читабельність і структуру коду. Якщо застосунку потрібно передати всі акустичні параметри треку в модель машинного навчання або на фронтенд, ми можемо витягти одразу весь об'єкт `audio_features`, замість того щоб перераховувати 12 окремих полів.
- _Коли створює проблеми:_ Якщо вкладеність стає занадто глибокою (більше 2-3 рівнів), це ускладнює написання запитів (потрібно постійно використовувати dot notation: `"audio_features.tempo"`) та може призвести до проблем із розміром документів або обмеженнями індексів.

**2. Чому виконавці зберігаються як масив, а не як рядок? Які запити стають простішими?**
Зберігання у вигляді масиву (`["Drake", "Future"]` замість `"Drake; Future"`) дозволяє MongoDB створювати ефективний Multikey індекс.
Якби це був рядок, пошук конкретного артиста вимагав би використання регулярних виразів (`$regex`), що призводить до повільного повного сканування колекції. Завдяки масивам ми можемо миттєво знаходити треки точним збігом, використовувати оператори `$in` (пошук кількох артистів), `$all` (пошук спільних треків), а також легко виконувати агрегації з `$unwind` (як у Завданні 2 Частини 2). --- ## 3. Індекси та оптимізація (Частина 3) ### Завдання 1: Аналіз запиту та індексація Створено складений індекс за правилом ESR: `track_genre` (Equality), `popularity` (Sort), `audio_features.danceability` (Range). _ **Що змінилося в плані виконання?** До оптимізації база виконувала повне сканування всієї колекції (`COLLSCAN`). Кількість переглянутих документів (`totalDocsExamined`) становила 114 000. Після створення індексу запит сканує виключно цільові документи: `totalDocsExamined` зменшився до 354. Час виконання (`executionTimeMillis`) впав із 85 мс до 2 мс (швидкість зросла у понад 40 разів). _ **Як зрозуміти, що індекс використовується?** У виводі методу `explain("executionStats")` на стадії `inputStage` значення поля `indexName` змінилося з `COLLSCAN` на `track_genre_1_popularity_-1_audio_features.danceability_1`. Це підтверджує, що рушій бази даних використав створений нами індекс (IXSCAN). ### Завдання 3 (Факультативне): Покривний запит (Covered Query) **Запит:** `db.tracks.find({ track_genre: "pop", popularity: { $gte: 70 } });`
**Індекс:** `{ track_genre: 1, popularity: -1, "audio_features.danceability": 1 }`

**Відповідь:** Ні, цей запит **не є покривним**.
**Обґрунтування:** Покривний запит (covered query) — це запит, у якому всі поля, що беруть участь у пошуку, і всі поля, що повертаються у результаті, повністю містяться в індексі. Оскільки в нашому запиті відсутня проєкція (projection), MongoDB за замовчуванням намагається повернути весь документ (усі поля, включно з `_id`, `track_name` тощо). Оскільки цих полів немає в індексі, базі доводиться звертатися до фізичних документів на диску (стадія FETCH). Щоб запит став покривним, його необхідно обмежити проєкцією: `{ _id: 0, track_genre: 1, popularity: 1 }`.
